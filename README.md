# ENA Field Guide

Practical, evidence-backed HOW for applying ENA-derived mechanisms in real Agent/Host work.

This repository is downstream of ENA research, but it is **not** a simplified copy of the ENA repository and it does not wait for ENA to become a final or perfect framework before it can grow.

## Role

ENA primarily asks:

> What relations, constraints, and mechanisms preserve viable self-evolving agency?

The Field Guide asks:

> When a recurring real problem appears, what should an Agent/operator actually do, what should it watch, and when should the pattern stop applying?

A typical entry should have a shape similar to:

```text
When X happens
-> do Y
-> watch Z
-> stop/revalidate when B changes
```

The exact format may evolve from use.

## Canonical content boundary

This repository owns **practical ENA application HOW**, not ENA theory and not general human-AI project-working method.

Do not duplicate upstream material.

```text
ENA theory / evidence
-> reference it; do not copy the theory here

Human-AI project method
-> belongs in Human-AI Workbench

ENA-derived operating HOW
-> belongs here
```

A Field Guide entry may include the minimum ENA explanation needed to apply a pattern safely, plus a pointer to its ENA evidence/provenance. It should not reproduce the research note, Constitution discussion, experiment history, or mechanism argument.

Likewise, ENA should not copy a complete Field Guide SOP back into the research repository. Reality use of a HOW may return new evidence to ENA, but the operating procedure remains owned here.

## Admission rule

A HOW may be added incrementally when it has enough support to be genuinely reusable. It does **not** need to wait for a final ENA release.

Prefer entries that have materially demonstrated:

- a real or repeatedly observed problem;
- a concrete reusable practice;
- evidence or reality contact beyond attractive theory alone;
- an explicit applicability boundary or counterexample;
- failure/monitoring conditions;
- practical value beyond the originating experiment/session.

Do not promote a research hypothesis, metaphor, one-off cleanroom answer, or elegant ENA phrase into a Field Guide HOW merely because it sounds actionable.

A useful admission check is:

> If the ENA theory link were removed, would the remaining entry still tell an Agent/operator what to do, when not to do it, and what to monitor?

If not, it is probably still research rather than Field Guide material.

## Relationship to other repositories

- `guytogay/evolution-native-agent-architecture` — ENA natural-law / architecture research, Current releases, falsification and field-validation evidence.
- `guytogay/human-ai-workbench` — canonical reusable human-AI project collaboration method, including continuation/handoff and lightweight experiment-working discipline when those methods generalize beyond ENA.
- validation cleanrooms — disposable or isolated experimental infrastructure, not reusable operating guidance by default.
- `guytogay/ena-field-guide` — practical ENA-derived HOW that has earned reuse.

The three repositories can feed one another without mirroring one another:

```text
real collaboration friction
-> Human-AI Workbench method
-> can return to support ENA and other projects

Agent phenomenon
-> ENA research / falsification / reality contact
-> reusable practical HOW
-> ENA Field Guide
-> later real use may return new evidence to ENA
```

## Growth model

Use evidence as the trigger:

```text
ENA phenomenon / mechanism
-> falsification and reality contact
-> reusable operating practice emerges
-> record the HOW here with scope and failure conditions
-> revise or retire it when later evidence changes its fitness
```

This repository should grow gradually as real practice earns entries. It should remain cheaper and clearer than the problems it helps solve.
